# CLAUDE.md

Guidance for Claude Code (or any AI coding assistant) working in this
repository.

## Architecture

```
label-qr-gui/      egui/eframe appliance. LabelApp holds the five
                    built-in fields (Client/Project/Location/ID/Name)
                    plus `extra: Vec<(ExtraFieldDef, String)>` loaded
                    from an optional `--config` TOML file (see
                    fields.example.toml). `payload()` serializes
                    everything as JSON for the QR code (always including
                    a `timestamp_utc` captured fresh on each draw),
                    `folder_name()` previews a
                    `<Client>-<Project>-<Location>-<ID>-<Name>` string
                    from the five built-in fields only -- extra fields
                    never affect it, only the QR's "extra" map. This is
                    just a human-readable on-screen hint, not literally
                    photo-splitter's output path (see below) -- the two
                    deliberately aren't kept in lockstep; if
                    photo-splitter's directory scheme changes again,
                    there's no requirement to update this string to
                    match. Client, like Project/Location, is NOT cleared
                    on "Next" (only Name and reset_on_next-flagged extra
                    fields are) -- it's meant to stay put across a whole
                    engagement the same way Project/Location do.
                    draw_qr() renders QR modules directly with
                    egui::Painter (no image/raster step) so the code
                    stays crisp and purely black/white at any window
                    size.
  web/index.html     Browser-based alternative front end, independent of
                    the Rust binary -- a single self-contained HTML file
                    (no build step/server/network access needed) that
                    reimplements LabelApp's logic directly in vanilla JS:
                    same five fields, same JSON payload shape/field
                    order/omit-when-empty rules as payload() above, same
                    Next semantics, same once-a-second repaint for
                    timestamp_utc. QR encoding is a vendored, unmodified
                    copy of Kazuhiko Arase's MIT-licensed qrcode-generator
                    (js/dist/qrcode.js from
                    github.com/kazuhikoarase/qrcode-generator), inlined
                    in its own <script> block rather than hand-written --
                    QR encoding (Reed-Solomon ECC, mask selection, format/
                    version info) is exactly the kind of thing worth
                    getting from a well-tested existing implementation
                    rather than reproducing from memory, given how easy a
                    subtle bug would be to miss until a real decode fails
                    in the field. Verified end-to-end (2026-11-26): a
                    payload generated by this page, round-tripped through
                    a hand-rolled PNG encoder in Node and decoded with
                    photo-splitter's actual decode_qr (rqrr + image, same
                    code path used for real photographed screens) via a
                    temporary test, came back byte-for-byte correct
                    including the `extra` map; the temporary test and its
                    fixture were removed afterward once confirmed, rather
                    than left in the suite (it depended on Node to
                    generate its fixture, which the Rust test suite has
                    no other reason to require). Extra fields are grouped
                    into named metadata sets (a project with more than one
                    kind of shoot can have one field list per kind rather
                    than a single fixed one) picked via the "Metadata Set"
                    dropdown; customization works like --config
                    fields.toml but via a JSON sidecar (fields.example.json
                    -> fields.json, `{"SetName": [{name, reset_on_next},
                    ...], ...}`, loaded with fetch() -- falls back to the
                    DEFAULT_FIELD_SETS object hardcoded near the bottom of
                    the file if that fetch fails, e.g. opened via file://
                    in a browser that blocks fetch() of local files) or by
                    editing DEFAULT_FIELD_SETS directly, which works
                    regardless of how the file was opened.
                    ensurePlainFieldSet() guarantees a no-extra-fields
                    "Plain" option always exists in the dropdown even if
                    the loaded config doesn't define one (checked
                    case-insensitively against "Plain"/"Default", or any
                    set that's already empty) -- there should always be a
                    quick way to skip extra fields entirely, the same as
                    not passing --config to label-qr-gui.

                    Separately from the QR code, the page also has an
                    SMPTE LTC ("timecode warble") generator for jam-
                    syncing a camera/recorder's audio input, toggled by
                    its own Start/Stop button and independent of
                    everything else on the page (the two features don't
                    interact). Bit-level frame format (which bits hold
                    frame/seconds/minutes/hours BCD fields, the 16-bit
                    sync word, biphase mark coding's transition rule) was
                    confirmed against SMPTE 12M's published layout, not
                    written from memory -- see the long comment directly
                    above `LTC_WORKLET_SOURCE` for the full bit table.
                    Seconds-tens and minutes-tens are **3-bit** fields
                    (24-26, 40-42; a 1-bit flag follows each, at 27/43) --
                    initially written as 2-bit fields (which can only
                    represent 0-3, not the 0-5 a tens digit needs), a bug
                    that produced completely plausible-looking output for
                    any tens digit 0-3 and only surfaced once a test
                    happened to start at :58 and decode back as :18 (see
                    the verification note below -- this is exactly the
                    kind of error a real decode catches that eyeballing a
                    waveform or counting total bits never would, since
                    2-bit-tens-plus-2-bit-flag and 3-bit-tens-plus-1-bit-
                    flag both sum to the same 64 bits). 29.97 Drop-Frame
                    is implemented (skips displayed frame numbers 0/1 at
                    the start of every minute not divisible by 10, sets
                    bit 10) alongside a separate 29.97 Non-Drop option
                    (simpler, drifts ~3.6s/hour from true wall-clock
                    time) -- see `firstValidFrame()`. Other user-bit/
                    flag-bit fields are left at 0 (unused) -- this only
                    needs to carry H:M:S:F (and drop-frame's bit 10)
                    correctly for an auto-sync tool to correlate separate
                    recordings' audio tracks.

                    Runs inside an AudioWorklet (loaded from a Blob URL,
                    not a second file, to keep this page single-file) --
                    a dedicated real-time-safe audio thread, chosen
                    specifically so ordinary page activity (typing,
                    layout, GC pauses) can never glitch the bit timing
                    the way running this on the main thread could.
                    Jam-syncs to the device's wall-clock time of day when
                    "Start Timecode" is pressed, then free-runs from
                    there using the AudioContext's own sample clock --
                    see the module comment for why that's the realistic
                    limit of "sync" without a hardware reference.

                    Verified by two independent means (2026-11-26), since
                    this is bit-level protocol code where a subtle error
                    could look fine on a waveform but decode wrong: (1)
                    ran the exact AudioWorkletProcessor source (extracted
                    from this file) in Node by stubbing `sampleRate`/
                    `AudioWorkletProcessor`/`registerProcessor`, driving
                    `process()` in a loop to generate real audio, written
                    to a WAV file; (2) decoded that WAV with an
                    independently-written Python biphase demodulator (reads
                    transition timings directly from the PCM samples,
                    estimating bit-cell duration from the data itself
                    rather than reusing any constant from the generator)
                    -- decoded frame numbers incremented by exactly 1 and
                    rolled over correctly across all four fps options, a
                    drop-frame minute boundary both where the skip should
                    (non-tens minute) and shouldn't (tens minute) happen,
                    and an hour/midnight rollover -- using starting values
                    that specifically exercise every tens digit 0-5 (not
                    just the first test's :20/:30, which is what let the
                    3-bit-field bug above slip past initially). Neither
                    harness is part of this repo. Separately confirmed via
                    a real headless-Chrome click on the Start Timecode
                    button that the whole pipeline (AudioContext creation,
                    worklet loading, message passing, readout update)
                    wires up and produces a correctly wall-clock-jam-
                    synced first tick -- continuous real-time playback
                    through actual audio hardware could not be verified in
                    this sandbox (no real audio output device, so headless
                    Chrome's audio render graph only processes an initial
                    burst rather than pacing in real time) and is worth a
                    quick manual check in an actual browser before relying
                    on this for a real multi-camera shoot.
                    `label-qr-gui --export-web <DIR>` (main.rs, not part
                    of web/index.html itself) embeds both files via
                    `include_str!` and writes them out verbatim instead of
                    launching the GUI -- exists so a `cargo
                    install`/crates.io install (no GitHub checkout) can
                    still get this page; see export_web()'s tests for the
                    byte-identity check against the embedded strings.
  src/ltc.rs         Native-audio port of web/index.html's
                    LTC_WORKLET_SOURCE, for the same Timecode Warble
                    feature in the native GUI -- `LtcGenerator` is a
                    direct line-by-line translation of the JS state
                    machine (build_frame_bits/first_valid_frame/segment-
                    stepping advance()), deliberately kept independent of
                    any audio I/O library so its correctness is testable
                    without a real device. main.rs's `start_ltc_stream`
                    is the only place that touches `cpal` (ALSA on
                    Linux, via flake.nix's `alsa-lib` -- a *build-time*
                    dependency here, unlike photo-splitter's ffmpeg,
                    since cpal links against libasound rather than
                    shelling out to a CLI tool). Keep the two
                    implementations in sync if either changes; ltc.rs's
                    own tests include a from-scratch Rust biphase
                    demodulator (independent of LtcGenerator's own bit-
                    stepping assumptions) that round-trips all four fps
                    options, both drop-frame skip and no-skip minute
                    boundaries, and a midnight rollover -- ported
                    straight from the JS version's validation approach,
                    and it came out correct on the first try specifically
                    *because* it was ported after the web version's 2-bit-
                    vs-3-bit tens-field bug (see web/index.html's doc
                    comment) was already found and fixed.
photo-splitter/     scans a directory of time-ordered photos (EXIF
                    DateTimeOriginal, falling back to mtime), decodes
                    each QR-marker frame via rqrr, applies configured
                    field defaults to any still-blank built-in field
                    (xmp::FieldDefaults::apply, see src/xmp.rs entry
                    below), and moves each group's files into
                    `<Client>/<Project>/<Location>/<Name>/<yyyy-mm-dd>/`
                    (`group_dir`), where the date is parsed from the
                    marker's `timestamp_utc`, not the photo's own EXIF
                    capture time (`group_date`). If that plain date path
                    is already taken (two shoots sharing Client/Project/
                    Location/Name on the same day -- a real case, not
                    just hypothetical, see below), `finish_group` retries
                    once at `<yyyy-mm-dd>_<ID>/` before giving up; a
                    collision at *that* path too still means a genuine
                    `bail!`. A metadata.yaml (the decoded LabelPayload,
                    serde_yaml) goes in the leaf directory alongside the
                    photos. Each group is buffered in `Group` and only
                    moved (`finish_group`) once the *next* marker or
                    end-of-directory is reached -- never move a file
                    before you know the group is complete. With
                    RUST_LOG=trace, dump_qr_debug_image() saves the exact
                    image handed to the QR detector for every photo into
                    a `_qr_debug/` folder next to it. Decoding all files
                    (the expensive part) and applying field defaults to
                    each happens in one
                    `entries.par_iter().map(|path| decode_qr(path,
                    ...).map(|mut label| { field_defaults.apply(&mut
                    label); label })).collect()` BEFORE the grouping
                    loop -- grouping itself must stay strictly
                    sequential (it depends on seeing markers in time
                    order), so it's cheap pure bookkeeping once `decoded`
                    already holds every file's (defaulted) result. If a
                    tag prefix resolves (xmp::resolve_tag_prefix), every
                    moved file also gets a <file>.xmp sidecar
                    (xmp::write_xmp_sidecar) written right after its
                    fs::rename, inside the same per-member loop in
                    finish_group.
  src/xmp.rs         Config loading (tag_prefix and FieldDefaults, from
                    --tag-prefix / --config / ~/.config/photo-splitter/
                    config.toml, in that precedence -- FieldDefaults has
                    no CLI-flag equivalent of its own, only the --config/
                    default-path path) and XMP sidecar generation.
                    Darktable hierarchical tags need TWO xmp fields
                    together -- confirmed against a real
                    Darktable-written sidecar, not guessed: dc:subject
                    (flat_tags -- every unique path *segment* across all
                    tags, deduplicated) and lr:hierarchicalSubject
                    (hierarchical_tags -- the actual pipe-joined
                    "prefix|Field|value" paths). hierarchical_tags skips
                    any built-in or extra field whose value is blank
                    (empty or whitespace-only) after FieldDefaults has
                    already had a chance to fill it in -- so "no default
                    configured for this field" and "omitted from the
                    sidecar" fall out of the exact same blank check, no
                    separate bookkeeping needed. ID and timestamp_utc are
                    deliberately not tagged (bookkeeping, not something
                    you'd browse by; still in metadata.yaml). Writes no
                    darktable:* processing-history attributes at all,
                    since these sidecars are for photos Darktable has
                    never seen -- this assumes Darktable's import reads
                    foreign/minimal XMP for metadata the way it does for
                    e.g. Lightroom sidecars, which hasn't been confirmed
                    against a real Darktable import (no Darktable
                    instance available to test with here), only against
                    the on-disk XMP format itself.
  src/raw_decode.rs  Two ways to get a grayscale image out of a RAW file
                    to scan for a QR code. `decode_default` (the
                    default) runs LibRaw's dcraw_process pipeline with
                    `params.half_size = 1` (block-average demosaic --
                    quarter resolution, skips the expensive AHD/VNG
                    interpolation entirely, since QR detection doesn't
                    need photo-quality output) via FFI bindings
                    generated in src/libraw_sys.rs -- this is the
                    "default light leveling and contrast" path, chosen
                    over the cheap EXIF-thumbnail route specifically
                    because thumbnails are often too small/absent (or
                    just frame too little of the QR within the shot),
                    and getting QR detection wrong silently merges two
                    shoots together. Confirmed against 21 real Canon CR2
                    files (2026-11-26): the EXIF-thumbnail path (--fast)
                    found zero markers; decode_default found them all.
                    `decode_thumbnail` (`--fast`) is the old cheap
                    fallback, kept for when a full LibRaw decode per
                    photo is too slow. See src/libraw_sys.rs's module
                    doc for why this is hand-bound via bindgen rather
                    than an existing crate (both `rawler` and the
                    published LibRaw Rust bindings were unsuitable --
                    checked 2026-11-26, worth re-checking if revisiting
                    this).
```

There is no `darktable-export` crate -- a stub was scaffolded early on
for what turned out to be XMP sidecar generation, but that job was
absorbed into `photo-splitter` directly (see `src/xmp.rs` above), and
the never-implemented stub was removed from the workspace entirely
(2026-11-26) rather than kept around undecided. If a separate import
step is ever needed (e.g. for Darktable grouping, which is `library.db`-
only and can't live in a sidecar -- see below), that's `darktable-
import-xmp`'s job, not something to re-add here.

## Grouping is library.db-only, not something a sidecar can carry

Confirmed via a still-open darktable issue (#16827) asking for exactly
this feature: Darktable's image grouping (`group_id`, where an image is
a group's representative iff `id == group_id`) lives only in
`library.db` -- rebuilding the library from XMP loses all manually-made
groups, because there's no stable way to encode "these N images are one
group" in a single image's own sidecar file. (A community Lua script,
`group_persistence`, works around this with specially-named tags, but
only while that exact script is installed/running in Darktable --
not something to build a tool's compatibility around.) If
`photo-splitter`'s output ever needs grouping in Darktable, the
reliable path is extending `darktable-import-xmp` to set `group_id`
directly when importing (it already sets `group_id = own id` for every
image today, i.e. explicitly ungrouped) -- not trying to encode it into
`xmp.rs`'s sidecars.

## The QR payload is JSON, not the dash-joined string

`label-qr-gui` encodes the QR as a JSON object (`{"client":...,
"project":..., "location":..., "id":..., "name":..., "timestamp_utc":...,
"extra":{...}}`), not as the
`<Client>-<Project>-<Location>-<ID>-<Name>` string shown in the UI
preview. JSON round-trips safely even if a field itself contains a dash,
and the `"extra"` map is open-ended (field names come from whatever
config file was used at capture time). Keep this split (JSON on the
wire, dash-joined string only as a human-readable on-screen hint -- not
a preview of photo-splitter's actual output path, which is a nested
`<Client>/<Project>/<Location>/<Name>/<yyyy-mm-dd>/` directory, not this
flat string; see photo-splitter's entry above).
`photo-splitter`'s `LabelPayload.extra` is a plain
`BTreeMap<String, String>` deliberately -- it must treat keys as
unknown/arbitrary, never assume a fixed schema -- and the field is
absent entirely when no extra fields were configured, not just empty
(`#[serde(default, skip_serializing_if = "BTreeMap::is_empty")]`
mirrors that on both sides).

`timestamp_utc` is not stored as app state -- it's computed fresh with
`Utc::now()` every time `payload()` runs. `ui()` calls
`ctx.request_repaint_after(Duration::from_secs(1))` unconditionally so
egui keeps redrawing (and thus recomputing the timestamp) even when the
form is left idle with no input, since the point is for the embedded
time to reflect whenever the screen is actually photographed, not
whenever it was last edited.

## Workflow notes

- `cargo fmt --all`, `cargo clippy --all-targets --all-features -- -D
  warnings`, and `cargo test` must all pass before committing. CI
  enforces the same three.
- `xmp::FieldDefaults` (`default_client`/`default_project`/
  `default_location`/`default_name` in the same config file as
  `tag_prefix`) exists so a missing/blank field doesn't produce an
  inconsistent `_`-sanitized path component across a whole client's
  shoots when the real value is actually always the same (e.g. one
  `photo-splitter` install that only ever processes one client's
  photos). It's deliberately config-file-only, with no `--default-client`
  CLI flag -- unlike `tag_prefix`, these aren't expected to vary
  per-invocation. Applied once per decoded label, inside the same
  `par_iter` pass as `decode_qr` (before grouping), so both `group_dir`
  and `xmp::write_xmp_sidecar` see the already-defaulted value; a field
  still blank after that (no default configured) flows through
  unchanged -- `sanitize` turns it into `_` in the path exactly as
  before, and `hierarchical_tags`'s existing blank-skip omits it from
  the XMP sidecar, so "no default" and "omit from the sidecar" require
  no separate logic.
- `xmp.rs`'s two-field hierarchical-tag structure (`dc:subject` +
  `lr:hierarchicalSubject`) isn't from Darktable's docs -- it's reverse
  engineered from a real Darktable-written sidecar the user pointed at
  directly (`~/Documents/Personal/Dropbox/Pictures/CanonRawPhotos/.../
  *.xmp`, a Dropbox sync mount -- keep any future look there to a
  single targeted file read, not a recursive grep/glob, it can be slow
  to materialize files). If revisiting this format, prefer checking
  another real sidecar over trusting written docs on the subject; the
  two don't agree on everything (e.g. docs suggested dc:subject might
  hold full hierarchical paths -- it doesn't, just flat segments).
- The same-day ID-disambiguation path (`group_dir`'s
  `disambiguate_with_id`) isn't just defensive coding -- it was added
  after hitting the exact collision for real during the first proper
  (non-dry-run) run against real camera files: two separate shoots both
  decoded to Project/Location/Name "Test2", on the same day, and the
  second one failed with `destination already exists` before this
  existed. The failing marker photo was identified by copying candidate
  files into an empty scratch dir one at a time and re-running
  `--dry-run` on each until the duplicate's group name showed up --
  simple and reliable when `RUST_LOG=trace`'s `_qr_debug/` dump doesn't
  immediately make it obvious which specific file is the culprit.
- `nix build .#label-qr-gui` / `.#photo-splitter` / `nix develop`
  should keep working; if you add a Cargo dependency, make sure
  `Cargo.lock` is committed so the Nix build stays reproducible. A new
  source file is invisible to a flake-from-git-checkout build until
  it's at least `git add`ed (staged, not necessarily committed) --
  this bit twice while building `raw_decode.rs`/`libraw_sys.rs`.
- `photo-splitter`'s `metadata.yaml` mirrors the decoded QR payload
  verbatim (same `LabelPayload` struct, serialized with `serde_yaml`)
  rather than inventing a second schema for the same data.
- `photo-splitter` moves files with `fs::rename`, which only works
  within a single filesystem -- it does not fall back to copy+delete
  across filesystem boundaries. The destination folders are always
  created as siblings inside the same directory being scanned, so this
  is a non-issue unless that assumption changes.
- `photo-splitter/tests/fixtures/` holds two real-camera files (Canon
  EOS 5D Mark IV, privacy-reviewed before committing -- see the comment
  above `fixture_path()` in main.rs's test module for what each one is
  and why): `near-black-no-marker.CR2` (a genuine RAW decode + the
  half_size+blur speed fix, regression-tested with a 15s time bound)
  and `real-camera-marker.jpg` (a real photographed-and-cropped QR,
  giving lens/lighting/JPEG-artifact coverage a synthetically rendered
  QR doesn't). Only these two, not the full 21-file set used to find
  and fix the issues below -- keep it that way; more fixtures means
  more repo weight (no Git LFS here) and more real-photo content
  permanently in git history, both deliberately kept minimal. Before
  trusting `photo-splitter` on a real shoot with a *new* camera,
  though, still repeat that kind of manual check against a handful of
  its actual RAW files -- these two fixtures don't cover every
  camera/sensor's quirks.
- **libraw_r links libgomp (OpenMP).** Combining rayon's per-file
  parallelism with LibRaw's own internal OpenMP parallelism
  oversubscribes badly -- confirmed in practice: 12 rayon workers each
  spawning their own ~12-thread OpenMP team produced 145 OS threads on
  a 12-core machine, all contending rather than working (CPU usage
  stuck around 150%, i.e. ~1.2 cores' worth of real work, the entire
  time). `OMP_NUM_THREADS=1` fixes this by leaving rayon as the only
  parallelism layer; both the Nix package (`postFixup` wrapProgram
  `--set-default`) and the dev shell set this already, so it only
  bites if you build/run outside of Nix entirely. Verify empirically,
  don't guess, if you ever revisit this: check `ldd` on the actual
  `libraw_r.so` being linked (there can be multiple outputs/paths for
  the same nixpkgs attribute -- `nix build nixpkgs#libraw` alone
  pointed at a `bin`-only output with no `.so` in it at all; the
  shared libraries were in `nixpkgs#libraw.lib`), and watch
  `/proc/<pid>/task/*/wchan` for `futex_do_wait` plus total CPU-time
  (sum of utime+stime across threads) vs wall-clock elapsed as the
  simplest way to confirm whether real parallelism is happening at
  all, before assuming code is at fault.
- A single file can make the whole batch look broken even when
  parallelism is working correctly -- observed: one 36MB file took
  10+ minutes alone while twenty 36-44MB files from the same camera,
  same session, each took 5-22 seconds, dominating a parallel batch's
  tail. **Root cause, confirmed by per-stage timing (2026-11-26): not
  LibRaw.** All four libraw_* calls (open_file/unpack/dcraw_process/
  make_mem_image) finished in ~1.3s combined even on the slow file --
  the cost was entirely in `rqrr::detect_grids()` afterward. The file
  was a near-black, ISO-12800 shot (ended up being this repo's
  `near-black-no-marker.CR2` fixture); heavy sensor noise in a dark
  frame creates huge numbers of spurious finder-pattern-like
  candidates for rqrr to individually check and reject, where a
  cleaner or brighter frame doesn't. **Fix:** `decode_qr` now runs
  `image::imageops::blur(&gray, 1.0)` immediately before
  `rqrr::PreparedImage::prepare` -- real QR patterns (large,
  high-contrast, structured) survive a mild blur fine, fine-grained
  noise doesn't. This took that file from 90+s to ~150ms with no
  change in detection results across all 21 real test photos.
  Tried first and rejected: `half_size` downscaling further (real risk
  -- these photos frame the whole desk, not a tight crop of the QR, so
  the QR's pixel margin isn't huge to begin with; shrinking it further
  risks reintroducing the exact too-small-to-read failure the
  EXIF-thumbnail path already has) and LibRaw's own `fbdd_noiserd`
  pre-demosaic denoise (tested at the max setting, zero measurable
  effect on this file -- whatever rqrr is reacting to isn't fixed by
  denoising the Bayer data pre-demosaic). If a future pathological file
  isn't fixed by the existing blur, re-run the same per-stage timing
  method before guessing: it's what found the real bottleneck here
  after an initial wrong guess (busy/detailed scene content) that
  didn't hold up.
- `RUST_LOG=trace` makes `decode_qr` dump the exact grayscale image it
  fed to `rqrr` into a `_qr_debug/` folder next to each source photo
  (`dump_qr_debug_image`/`write_qr_debug_image`), for diagnosing why a
  marker frame wasn't recognized. This is deliberately gated behind
  `trace`, not `debug`, since it writes a file per photo rather than
  just a log line -- don't lower that threshold without good reason.
  Note for tests: `log::log_enabled!` consults the *installed logger's*
  `enabled()`, not just `log::set_max_level` -- the default no-op
  logger (when nothing has called `set_logger`/`env_logger::init`)
  always reports disabled regardless of max level, so a test
  exercising this path needs a real logger installed (e.g.
  `env_logger::Builder::new().filter_level(..).is_test(true).try_init()`),
  not just `log::set_max_level`.
- `libraw_sys.rs`'s bindings are regenerated by `build.rs` on every
  build (not checked in), via `bindgen` against whatever `libraw_r`
  pkg-config resolves to. If a field/function name changes (e.g. after
  bumping the LibRaw version in `flake.nix`), the fix is almost always
  in `raw_decode.rs`'s call sites, not in the generated bindings.
